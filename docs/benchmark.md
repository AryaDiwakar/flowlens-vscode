# Benchmark methodology

Run `python benchmarks/run_benchmark.py --split evaluation` from a Python environment with the backend dependencies installed. The script generates a temporary project from a seeded RNG, runs the real parser/scanner/graph/profiling/anomaly/investigation engines, computes metrics from declared synthetic ground truth, and writes an actual JSON report under `benchmarks/reports/`. `--split development` uses a different default seed; `--seed` and `--output` are available for reproducibility.

The fixture injects a broken join, `SELECT *`, an explicitly unmapped upstream table, a cycle, null/duplicate/range quality failures, a new schema column, numeric/null/category profile shifts, a row-count anomaly, and a configured KPI deviation. The suite measures SQL finding precision/recall/F1, lineage edge and unresolved-mapping precision/recall/F1, quality failure counts, schema changes, KPI signal detection, anomaly precision/recall/average precision/false-positive rate, root-cause top-1/top-3/MRR, cycle detection, initial and warm incremental scan latency, profile latency, and Python traced heap. `tracemalloc` does not include native DuckDB allocations. These tiny, directly labeled scenarios are smoke benchmarks, not production accuracy estimates; perfect scores on them do not generalize. Incremental scan timing is one changed SQL file in a warm backend process. Reports under `benchmarks/reports/` are outputs of the command and include limitations.
